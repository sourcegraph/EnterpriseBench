Sourcegraph Code Finder · benchmark evidence

Where Code Finder pays

On multi-repo retrieval tasks, Code Finder cuts an agent's input tokens by roughly five times with no measurable loss in answer quality. The saving is not a constant. It scales with how much ground the agent would otherwise have to cover, because Code Finder's own spend barely moves.

90 runs, primary arm 92 runs, replication arm 2 harnesses gpt-5.6-sol · claude-sonnet-5 EnterpriseBench · CodeScaleBench

The claim

On retrieval tasks that span more than one repository, replacing an agent's own search loop with a single Code Finder call cuts input tokens to 0.18× while task score holds at −0.019, an interval that spans zero.

Conditions the claim is scoped to

  • min_repos ≥ 2The task's answer lives in more than one repository.
  • min_required_files ≥ 3At least three distinct files must be found.
  • max_disclosed_fraction ≤ 0.25The prompt gives away no more than a quarter of the answer.
  • min_unreached_required_files ≥ 2At least two required files are not reachable by grepping literals lifted from the prompt.

These four conditions were written into configs/retrieval_stress_set.json and fixed before any of these runs happened. None of them mentions Code Finder, tokens, or cost, so the selection cannot have been fitted to the result it produces.

The control arm is the uncomfortable one and it belongs in the post. Handing the agent Sourcegraph's search tools without Code Finder made it worse on token spend: 1.14× the baseline, and 3.4× the tool calls, because the agent enumerates through a tool interface instead of composing a pipeline in a shell. Code Finder is not a thin wrapper over those tools. It is the thing that makes them pay.

Mechanism

Code Finder's spend is flat; the baseline's is not

This is the whole result in one picture. Each point is one task: what the baseline agent spent on the horizontal axis, what the Code Finder agent spent on the vertical. If the tool saved a fixed percentage, the points would track the dashed parity line. Instead they flatten into a band, because a Code Finder call costs about the same no matter how hard the task is.

Token spend per task, both arms

Fitting the flatness

Regressing log spend on log spend gives an exponent: 1.0 would mean Code Finder costs a fixed fraction of the baseline, 0.0 that it costs the same on every task regardless.

Both arms land near zero. Across a tenfold swing in baseline difficulty, Code Finder's spend varies by a coefficient of variation of about 0.2 while the baseline's varies by 0.7 to 0.8. That is what makes the saving predictable in direction and variable in size: you can say which tasks it will help, and the answer is the expensive ones.

Replication

A second harness, a second model, a second corpus

The same law shows up where nothing else is shared. The replication arm runs claude-sonnet-5 instead of gpt-5.6-sol, on tasks converted out of CodeScaleBench instead of EnterpriseBench, scored by CodeScaleBench's own oracle rather than ours. It also deliberately breaks the selection rule: every one of its 46 tasks is single-repository, so none of them would qualify for the claim above. That makes it the negative control as well as the replication.

Why the dollar column is milder than the token column

96.1% of the baseline arm's context is prompt-cache reads, billed at a tenth of the input rate. Under caching a large token saving compresses into a smaller bill. Both columns are true; they answer different questions. Tokens answer "will this fit in the context budget", dollars answer "what does the invoice say". A page that quotes one should say which.

Where the claim stops being true

Below about 400k baseline tokens Code Finder is a net cost: the token ratio is 1.012×, the bill goes up 1.24×, and score drops 0.224. A Code Finder call has a floor of roughly 200k tokens, and on a task the agent could have finished in 250k that floor is the whole budget. On the unselected corpus these cheap tasks drag the corpus-wide average to 0.607× tokens and a real quality penalty of −0.074. Quoting that corpus-wide number as the headline would understate the tool where it works and overstate it where it doesn't.

Limits

What this evidence does not support

Confounded

The multi-repo and single-repo arms differ in harness, model and corpus at once. What is measured cleanly inside each arm is the scaling law, and that replicates. "Multi-repo tasks are where the saving lives" is supported by the two arms together, not proven by a controlled contrast.

No selector

Inside a single-repository corpus, no task feature we could compute before running predicted the saving: required files r=−0.00, prompt literals r=−0.21, files unreachable by grep r=+0.02, unreachable fraction r=+0.25 (n=46). Repository count is the only a priori signal that worked.

Tokens only

The primary arm carries no dollar figure. The cost tracker has no rate card for gpt-5.6-sol, so that arm is reported in tokens and the dollar column comes from the replication arm alone.

Non-adoption

The replication corpus started at 55 paired tasks. On 9 of them the agent never called Code Finder, in the arm that exists to make it available; those runs were routed invalid rather than scored, which is what leaves 46 pairs here. Availability was 100% and use was 84%. That gap is a product fact worth its own investigation, and it is also a possible selection effect: if the agent skipped the tool on tasks where it would not have helped, the surviving pairs flatter it.

Sample

Ten tasks, three repetitions each, in the primary arm. Intervals use the t multiplier for that sample size, not the normal approximation. The score interval spanning zero means no penalty was detected, which is weaker than showing there is none.

Score

"Task score" is the benchmark's retrieval-and-answer composite against a fixed ground truth, not a human quality rating. It rewards naming the right files and reporting the right relationships between them.

Reproduce

Every figure on this page, from the run artifacts

The dataset is frozen from the raw run directories, the analysis reads only the frozen dataset, and this page is generated from it. No number here was typed by hand.

# freeze the dataset from results/runs/
python3 experiments/code_finder_scaling/build_dataset.py

# recompute every figure on this page
python3 experiments/code_finder_scaling/analyze.py

# pin the paired statistics and the arm contract
PYTHONPATH=lib python3 -m pytest tests/test_code_finder_scaling.py -q

# regenerate this page

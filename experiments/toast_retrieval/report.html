EnterpriseBench Search policy evaluation 2026-08-17

Should Toast-1 Join Our MCP Server

Mixedbread's Toast-1 is a model trained specifically as a search policy. We ran it against code_finder and deepsearch over the same Sourcegraph index, on 63 tasks whose prompts do not name the files being looked for. It loses to both by roughly 0.2 recall, it is the least stable of the three across repeats, and a model-swap ablation puts the deficit in the model rather than in its access to the index. One earlier conclusion reversed: on the harder corpus Toast-1 does find files code_finder misses.

Replace code_finder? No

0.435 mean recall against code_finder's 0.627 on the hard slice, losing every repo-count stratum, with twice the zero-recall tasks. A repeat of the same sweep scored 0.331, so 0.435 is the optimistic reading.

Augment code_finder? Open

Toast-1 contributes a required file code_finder missed on 9 of 63 tasks, worth +0.064 union recall. Two policies we already ship do better on that same axis (+0.081), which is the bar a third policy has to clear.

The engine, with internal access? No

A frontier model over Toast-1's own external tools matches code_finder per-task on 17 of 20 and never beats it. The access lever measures ~0.03; the model gap is the rest, and better access has no headroom to buy it back.

Worth knowing anyway Yes

On hard tasks code_finder and deepsearch converge (0.627 vs 0.633, inside repeat noise) and deepsearch costs 10x the latency for it. That is a result about two things we already ship.

Three policies, one index

A search policy takes a task, decides its own queries, and returns the files that matter. All three here got the identical task text, were scoped to the identical repositories, and were scored by the same IR functions against file-level ground truth authored independently of this experiment.

Read these numbers, not the 20-task corpus we started on. A third of that corpus names its own required files inside the task prompt, which manufactures agreement between policies and inflates every score. Each task here keeps at most a third of its required files namable from the prompt, and 44 of the 63 disclose nothing at all.

Volume control

Not just more files

Returning more files flatters raw recall, so the gap was re-measured with code_finder truncated per task to Toast-1's own set size. On the 20-task corpus that still gives 0.717 against 0.575. On the hard slice the volume difference is small to begin with: 9.4 files against 8.9.

Failure shape

Zeros, not near-misses

Toast-1 returns nothing relevant on 14 of 63 tasks, rising to 26 on the repeat. deepsearch fails outright on 5. For infrastructure, an intermittent total miss is a different problem from a lower average, and a worse one.

The corpus was naming its own answers

The first version of this comparison ran on 20 tasks and concluded that Toast-1 found nothing code_finder missed, on every task. That conclusion did not survive a check of the corpus. A tiered matcher (exact path, then path stem, then basename) against each task's own prompt found that a third of the required files are named in the prompt the agent receives. A policy that reads the prompt carefully scores on those without retrieving anything, and every policy reads the prompt, so scores compress toward each other.

The hard slice was selected by that measurement: 63 tasks at or below 1/3 disclosure, 44 of them naming nothing, every repository already indexed. Disclosure is now computed at selection time and enforced in CI, so a new task cannot quietly rejoin the leaky set.

The reversal. On the leaky corpus, adding Toast-1 to code_finder lifted union recall by +0.000, on 20 of 20 tasks. On the hard slice it lifts by +0.064, contributing a required file code_finder missed on 9 of 63 tasks. An independent repeat reproduces it: +0.056, again on 9 of 63, and 6 of those tasks are the same tasks in both runs. "Strict subset" was an artifact of shared prompt strings, not a property of the policies.

Did the scorer count what the policies found?

A recall number is a retrieval measurement only if the emitted paths are real and the scorer credits the ones that match. Neither had been checked, and one of them was wrong.

The metric library normalizes paths by stripping one leading segment unless it is on a 22-name allowlist (src, lib, pkg, cmd, …). Ground truth is repo-qualified for part of the corpus and repo-relative for the rest; retrieval output is uniformly repo-relative. For a repo whose top directory is not on that list (sdk, httpx, axum, packages, source, fastapi), ground truth loses only its repo name while the retrieved path loses a real directory: 

ground truth  otel-go/sdk/trace/batch_span_processor.go  →  sdk/trace/batch_span_processor.go
retrieved             sdk/trace/batch_span_processor.go  →      trace/batch_span_processor.go

A correct retrieval scored as a miss. Every sweep on disk was re-scored offline against a matcher that compares path suffixes in either direction, so it does not care which side carries the repo name. Pre-fix values are kept in each report, and corrected reports carry a scoring-contract stamp that the comparison script refuses to read without.

 The correction is not a constant offset. It depends on each repo's top-level directory name and on the citation form each policy emits, which is why the uncorrected numbers were a confound rather than a scale factor. The code_finder-to-Toast gap widens from 0.156 to 0.192.

A suffix matcher can over-credit, and a first pass did. Two constraints close that, each answering a false credit found in the reports: the prefix it will discard is bounded at two components (a repo name plus at most one source root), which stops a vendored copy of another project's file from being credited as that file; and assignment is one-to-one, so a path like pkg_resources/__init__.py cannot claim both setuptools' copy and pip's vendored one in the same task. Neither constraint changed a published score, because every real credit also came from a citation exact enough to survive them.

Do the emitted paths exist?

Every (repo, path) pair from the three hard-slice sweeps was checked against the same index the policies searched, in two stages: an exact blob lookup, then, for anything that failed it, a search for any file in the repo ending with that path. The second stage matters: sansio/app.py is a real Flask file cited without its src/flask/ prefix, which costs precision but is a real retrieval, not an invention.

 "Guessable root files" counts credited required files whose names are repo-root conventions (package.json, go.mod, .go-version), which score the same whether a policy searched for them or named them from memory. At 5–8% everywhere it does not move the ranking.

Toast-1 emitted zero paths that do not exist. Every path it returned is a real file, which is what a retrieval policy over a real index should produce and is a point in its favour that the recall numbers do not show. deepsearch invents the most, and the inventions are plausible rather than obvious: a Django migration filename that was never created, Modules/_ssl.c (a CPython file) in a requests task.

What this cannot check is whether an existing, non-guessable path was reached by a tool call or recalled from training. That needs the tool-call transcript. Our Toast runner persists only the returned paths and token counts; the MCP runner persists the model's prose, not its calls. It is filed as a gap rather than argued away, and it is the one instrumentation change that would make these numbers fully auditable.

Whose fault was 0.575?

The product comparison carries a confound it can name but not remove: Toast-1 reached the index through our adapter, while code_finder has Sourcegraph-internal access. So a fourth arm holds the tools fixed and swaps the model. Claude (anthropic/claude-sonnet-5) drives the exact retrieval seams Toast-1 drove, with the same task text, the same 4-round budget Toast-1 used on every task, and the same sampling parameters. This arm has run on the 20-task corpus only, so its numbers are on that corpus throughout.

Claude over the external adapter posts per-task recall identical to code_finder on 17 of 20 tasks and never beats it. Its losses are tasks where it answered the forced final round with an empty file list: those instructions end by demanding a written report, and the model punted rather than answer with files, the same deliverable mismatch code_finder showed when it apologized about a file it could not write.

The readout: access was not the bottleneck. A general model recovers nearly the whole Toast-to-code_finder gap over the same tools Toast-1 had, so what remains is the model, measured on the tool surface Toast-1 was purpose-trained for. Cost does not reopen it. Toast-1 ran at roughly a fifth of claude-over-adapter's per-task price, but 0.639 against 0.824 recall is not a trade.

The side finding stands on its own: four rounds of a frontier model over a thin external adapter (natural-language search, grep, file read, file list) matched a shipped agentic product task-for-task on this corpus. Whatever code_finder spends beyond that budget bought nothing measurable here.

The ranking survives every repeat: Toast-1 never beats code_finder in any run, and since its published number is its best run, the three-repeat means put the gap at 0.523 against 0.800, wider than the headline. Toast-1 is also the least stable policy measured, and the hard slice makes that worse, not better: 0.435 and 0.331 across two identical sweeps, zero-recall tasks going from 14 to 26, and 35 of 63 tasks changing score.

That matters independently of the mean. A search layer that intermittently misses a required file forces every caller to re-verify everything it returns, which is a worse property for infrastructure than a uniformly lower score. It also sets the floor for reading any single sweep: two policies on this corpus differ by roughly ±0.13 of run-to-run noise, which is wider than the entire code_finder-to- deepsearch gap on the hard slice.

code_finder against deepsearch

The comparison we did not set out to run is the one with a product decision attached. On the leaky corpus code_finder looked clearly ahead. On the hard slice the two converge: 0.627 against 0.633 recall, 0.594 against 0.593 at R@10, inside the repeat noise measured above. They differ in shape rather than in level. code_finder gets more tasks perfectly right (21 against 17); deepsearch fails outright on fewer (5 against 9) and is the more stable of the two.

Latency is where they separate, and it is not close: 22 seconds median against 221, 31 against 331 at p95. deepsearch also invents the most nonexistent paths of any policy measured. Adding it on top of code_finder does buy the largest complementarity in this study (+0.081 union recall, on 14 of 63 tasks), so the pair has a case; a 10x latency bill for it is the thing to weigh.

Output format instability

Both MCP policies cite files in three different formats, and which one a response uses varies per call with no field indicating which to expect: 

1. a fenced JSON block   {"files": [{"repo": "...", "path": "gcc/passes.def"}]}
2. markdown blob links   [routing.py](/r/<repo>/-/blob/fastapi/routing.py?L196-L249)
3. bare inline code      `fastapi/routing.py:227-264`

This cost us two full sweeps. A parser reading only form 1 scored 19 of 20 tasks as zero retrieved files. Adding form 2 still left 6 at zero, all of which had cited their files in form 3. Nothing about a zero-file parse looks like a bug from the caller's side; it looks like a policy that found nothing.

Separately, sg_code_finder takes one task string, and these tasks are full agentic prompts. Six responses opened by explaining that the tool could not write /workspace/analysis/IMPACT_REPORT.md because it only has search and read access. It then did the retrieval anyway, so the scores stand, but the tool is partly reading its input as instructions to execute rather than as a retrieval brief.

A stable machine-readable field for cited files would remove an entire class of silent integration failure. Any MCP client scoring or chaining on these results is writing the same fragile parser we did, and will get the same quiet zeros.

What would change these numbers

  • The access comparison assumes code_finder's inner model is Claude-class. It is unconfirmed. If it is materially stronger, the "access lever is small" reading overstates; the model-vs-model half of the ablation (Toast-1 against Claude on identical tools) does not depend on it.
  • The ablation arm has not run the hard slice. Its OpenRouter key hit a spend limit mid-repeat. Its numbers are on the 20-task corpus, which is the corpus this study otherwise demotes, so read it as a directional answer to "model or access?" rather than as a fourth column of the headline table.
  • Retrieval is credited without a trace. Path existence is verified against the live index, and Toast-1's rate of nonexistent paths is zero, but no runner persists the tool calls. An existing, non-guessable path recalled from training scores the same as one that was searched for. Instrumenting the transcript is the next change to the harness.
  • The adapter mapping is worth up to 0.12 mean recall. Three sweeps varying only how Toast-1's retrieval call maps onto Sourcegraph moved recall substantially and changed 13 of 20 task outcomes. Toast-1 is reported at its best measured mapping; the gap to code_finder is roughly 1.6x that confound on the hard slice.
  • 63 tasks, strata of 16 / 35 / 12. The headline gap and the instability result clear that sample comfortably. The per-stratum magnitudes and the +0.064 complementarity are indicative, which is why the complementarity was checked against a second independent run rather than reported from one.
  • Toast-1 token counts are exact. Mixedbread's API reports real usage per call, and dual accounting shows the reported totals match the provider's ledger integer-for-integer. The MCP policies' internal token spend is Sourcegraph-side and unobservable; their cost is measured as wall clock.

Method: each policy received the same task text and repo scope, and returned a set of files. Sets were scored with EnterpriseBench's IR functions against pre-existing file-level ground truth, read through a single shared extractor so no policy is advantaged by how ground truth is parsed, and through one path matcher applied identically to every arm.

Runners, per-task reports with raw responses and full ablation transcripts, the disclosure gate, the path-existence audit, the re-scorer, and their tests are in experiments/toast_retrieval/. Neither MCP policy needs a container or an agent account; both are direct tool calls, and the ablation arm runs over OpenRouter.
